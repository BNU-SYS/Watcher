### CWE-401: Missing Release of Memory after Effective Lifetime

- Use this type only for dynamically allocated memory whose ownership is lost or whose release is missing. Identify the allocation, owner, matching `free`/`delete`/`delete[]` or documented release, and a reachable exit without it.
- Check returns, cleanup labels, partial initialization, allocation failure paths, reassignment that loses the original pointer, C++ RAII, smart pointers, containers, and explicit ownership transfer. A local allocation reaching visible function exit without release is a finding unless the source visibly returns or transfers it.
- Track each dynamic memory object's ownership and effective lifetime along every relevant feasible path. Establish its final state on that path rather than merely checking whether release appears somewhere in the source. Release or ownership transfer on one path does not establish that another path handles the object safely.
- Distinguish using an object, changing references, releasing it, and transferring ownership. Using the object, changing a local reference, or leaving a scope does not by itself prove that dynamic memory was released or acquired by another owner. Require visible evidence of release, ownership transfer, or automatic lifetime management.
- Do not classify a file/socket/handle leak or unspecified resource as `CWE-401`. A failed allocation does not leak memory never obtained.
- A local or global allocation whose only visible owner is overwritten, discarded, or reaches visible function exit without release is sufficient. Do not infer hidden cleanup.

#### Finding location

- The primary operation is the allocation that produced the leaked block. For successful `realloc`, use that call when its returned block is leaked; a failed `realloc` creates no new block, so a leaked original block points to its original allocation. Explain ownership propagation and the losing or exit path.
